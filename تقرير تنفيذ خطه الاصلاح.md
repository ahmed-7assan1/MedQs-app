## Phase 1.2 — نقل PDF Cache من `globalThis` إلى Redis

### الهدف
PDF cache كان في `Map` داخل الذاكرة (يختفي مع كل cold start). نقله إلى Redis يرفع hit rate من ~60% إلى 90%+.

### المشكلة
- **قبل:** `src/lib/session-cache.ts` يستخدم `new Map<string, PdfCacheEntry>()`
- كل Vercel instance لها cache منفصل
- الـ cache يتلاشى مع cold start
- `setInterval` للتنظيف كل 5 دقائق (حتى لو ما في طلبات)

### التنفيذ

**1. إعادة كتابة `src/lib/session-cache.ts`:**
- **قبل:** Map + setInterval
- **بعد:** دوال async تستخدم Redis
- الحذف الآلي يتم عبر TTL في Redis (ما عاد في setInterval)

**الكود الجديد:**
```typescript
import { cacheGet, cacheSet, cacheDel } from "@/lib/redis";

export type PdfCacheEntry = {
  paragraphs: string[];
  lectureId: string;
  userId: string;
};

export const PDF_CACHE_TTL_SECONDS = 1800; // 30 minutes
const CACHE_PREFIX = "pdf:";

export async function getCachedPdfText(cacheKey: string): Promise<PdfCacheEntry | null> {
  const raw = await cacheGet(cacheKey);
  if (!raw) return null;
  telemetry.pdfCacheHit++;
  return JSON.parse(raw) as PdfCacheEntry;
}

export async function setCachedPdfText(cacheKey: string, entry: PdfCacheEntry): Promise<void> {
  await cacheSet(cacheKey, JSON.stringify(entry), PDF_CACHE_TTL_SECONDS);
}

export async function clearCachedPdfText(cacheKey: string): Promise<void> {
  await cacheDel(cacheKey);
  telemetry.pdfCacheCleared++;
}
```

**2. تحديث `chat/route.ts`:**
- استبدال `pdfTextCache.get(cacheKey)` → `await getCachedPdfText(cacheKey)`
- استبدال `pdfTextCache.set(cacheKey, {...})` → `await setCachedPdfText(cacheKey, {...})`
- إزالة معاملات `lastAccessed` و `PDF_CACHE_TTL` (Redis يتولى TTL)

**3. تحديث `clear-session/route.ts`:**
- استبدال `pdfTextCache.delete(pdfKey)` → `await clearCachedPdfText(pdfKey)`
- إزالة `telemetry.pdfCacheCleared++` (الوظيفة الجديدة تتعامل معها)

### الملفات المعدلة
| الملف | التغيير |
|---|---|
| `src/lib/session-cache.ts` | إعادة كتابة كاملة — Redis بدل Map |
| `src/app/api/v1/ai/chat/route.ts` | استدعاءات async جديدة |
| `src/app/api/v1/ai/chat/clear-session/route.ts` | استيراد `clearCachedPdfText` |

```typescript
const reader = response.body!.getReader();

  const { done, value } = await reader.read();
```

## Phase 2.1 — Lightweight Queue (waitUntil)

### الهدف
تفويض المهام الثانوية (Firebase sync, إشعارات) لما بعد إرسال الـ response للمستخدم.

### المشكلة
المهام زي:
- تسجيل engagement (نقاط المستخدم)
- Firebase real-time mirroring
- إرسال إشعارات broadcast

كلها كانت **تتم قبل إرسال الـ response**، يعني المستخدم ينتظرها.

### التنفيذ

**1. إنشاء `src/lib/defer.ts`:**
```typescript
import { waitUntil } from "@vercel/functions";

export function defer(fn: () => Promise<unknown>) {
  try {
    waitUntil(fn().catch((err) => {
      if (process.env.NODE_ENV === "development") {
        console.warn("[defer] task failed:", err instanceof Error ? err.message : err);
      }
    }));
  } catch (err) {
    if (process.env.NODE_ENV === "development") {
      console.warn("[defer] waitUntil unavailable:", err instanceof Error ? err.message : err);
    }
  }
}
```

**مزايا التصميم:**
- error handling كامل (ما يخلي الـ response يفشل لو المهمة فشلت)
- يعمل في development و production
- silent fail — المهام الثانوية تفشل بصمت

**2. تطبيق في `src/app/api/v1/forums/[forumId]/posts/route.ts`:**

**قبل (synchronous):**
```typescript
// Log engagement points
prisma.engagementLog.create({ data: { userId, action: "post", points: 5 } }).catch(() => {});
prisma.user.update({ where: { id: userId }, data: { points: { increment: 5 } } }).catch(() => {});
// Firebase sync
const { adminDb } = await import("@/lib/firebase/admin");
const firestorePost = JSON.parse(JSON.stringify(returnPost));
await adminDb.doc(`forums/${forumId}/posts/${post.id}`).set(firestorePost);
return NextResponse.json(returnPost, { status: 201 });
```

**بعد (deferred):**
```typescript
defer(async () => {
  await Promise.allSettled([
    prisma.engagementLog.create({ data: { userId, action: "post", points: 5 } }),
    prisma.user.update({ where: { id: userId }, data: { points: { increment: 5 } } }),
  ]);
  try {
    const { adminDb } = await import("@/lib/firebase/admin");
    const firestorePost = JSON.parse(JSON.stringify(returnPost));
    await adminDb.doc(`forums/${forumId}/posts/${post.id}`).set(firestorePost);
  } catch (firebaseErr) {
    console.error("[POST-API] Firestore sync failed:", firebaseErr);
  }
});
return NextResponse.json(returnPost, { status: 201 });
```

**3. تطبيق في `src/app/api/v1/notifications/read-all/route.ts`:**

**قبل:**
```typescript
await broadcastNotification(userIds, { title, body, channel: "BROADCAST" });
return NextResponse.json({ sent: userIds.length });
```

**بعد:**
```typescript
defer(() => broadcastNotification(userIds, { title, body, channel: "BROADCAST" }));
return NextResponse.json({ sent: userIds.length });
```

- بعد 30 طلب في الدقيقة، المفتاح الأول يجيب 429، ثم يتحول للثاني، وهكذا
- هذا معناه: 30 RPM فعلي، استجابة غير متوقعة

### التنفيذ

**1. إنشاء `getGeminiApiKeys()` في `src/lib/gemini-keys.ts`:**

```typescript
let currentIndex = 0;

export function getGeminiApiKeys(): string[] {
  const keys = [
    process.env.GEMINI_API_KEY_1,
    process.env.GEMINI_API_KEY_2,
    process.env.GEMINI_API_KEY_3,
    process.env.GEMINI_API_KEY_4,
    process.env.GEMINI_API_KEY_5,
  ].filter(Boolean) as string[];
  return keys;
}

export function getNextGeminiKey(): string {
  const keys = getGeminiApiKeys();
  const key = keys[currentIndex % keys.length];
  currentIndex++;
  return key;
}
```

- `currentIndex` يتقدم مع كل طلب
- كل طلب يستخدم مفتاح مختلف (A → B → C → D → E → A → ...)

- إذا المفتاح المشفر فشل فك التشفير، يرجع `null` بدل ما يمرر garbage للـ API

```typescript
export function looksEncrypted(value: string): boolean {
  return value.startsWith("aes-256-gcm:") || 
         (value.length > 100 && /^[A-Za-z0-9+/=:]+$/.test(value));
}
```

## Phase 2.3 — توسيع Auth Cache في Redis

### الهدف

### المشكلة
- 110+ API route تستدعي `getSessionScope()` 
- كل مرة: query لقاعدة البيانات لـ `universityId`, `semesterId`, `facultyId`, `isLeader`, `role`
- 5 حقول صغيرة، لكن تتكرر مئات المرات في الثانية

### التنفيذ

**تعديل `src/lib/tenant.ts`:**

```typescript
const SCOPE_CACHE_TTL = 300; // 5 minutes

export async function getSessionScope(session: Session | null): Promise<SessionScope | null> {
  const userId = session?.user?.id;
  if (!userId) return null;
  
  // Try Redis first
  const cacheKey = `scope:${userId}`;
  const cached = await cacheGet(cacheKey);
  if (cached) {
    return JSON.parse(cached) as SessionScope;
  }
  
  // Fallback to DB
  const db = await prisma.user.findUnique({ ... });
  
  const scope: SessionScope = { ... };
  
  // Cache in Redis
  await cacheSet(cacheKey, JSON.stringify(scope), SCOPE_CACHE_TTL).catch(() => {});
  
  return scope;
}
```

**وظيفة إضافية للإبطال:**
```typescript
export async function invalidateSessionScope(userId: string): Promise<void> {
  const { cacheDel } = await import("@/lib/redis");
  await cacheDel(`scope:${userId}`).catch(() => {});
}
```

## Phase 2.4 — إصلاح Firebase Sync

### الهدف
بدل ما يسوي `syncAllThreadsToFirestore` كل 2 ثانية (يكتب كل الـ threads في batch واحد)، يحفظ فقط أحدث thread.

### المشكلة
- **قبل:** `src/hooks/useDrQChat.ts` كان يستدعي `syncAllThreadsToFirestore(userId, threads)` كل 2 ثانية
- هذا الدالة تأخذ كل الـ threads (قد تصل إلى 50+ thread) وتكتبهم في batch إلى Firestore
- هدر في الكتابة (network + quota)
- المستخدم حالياً 5–10 threads، لكن لو كبرت المشكلة تزيد

### التنفيذ

**في `src/hooks/useDrQChat.ts`:**

**قبل:**
```typescript
import { syncAllThreadsToFirestore, subscribeToThreads, deleteThreadFromFirestore } from "@/lib/firebase/firestore";

useEffect(() => {
  if (!userId || threads.length === 0 || loading) return;
  const timeoutId = setTimeout(() => {
    syncAllThreadsToFirestore(userId, threads); // يكتب كل threads!
  }, 2000);
  return () => clearTimeout(timeoutId);
}, [threads, userId, loading]);
```

**بعد:**
```typescript
import { saveThreadToFirestore, subscribeToThreads, deleteThreadFromFirestore } from "@/lib/firebase/firestore";

useEffect(() => {
  if (!userId || threads.length === 0 || loading) return;
  const timeoutId = setTimeout(() => {
    // Only sync the most recently updated thread instead of all threads
    const latest = threads.toSorted((a, b) => b.updatedAt - a.updatedAt)[0];
    saveThreadToFirestore(userId, latest);
  }, 2000);
  return () => clearTimeout(timeoutId);
}, [threads, userId, loading]);
```

### الملفات المعدلة
| الملف | التغيير |
|---|---|
| `src/hooks/useDrQChat.ts` | استبدال `syncAllThreadsToFirestore` بـ `saveThreadToFirestore` لأحدث thread فقط |

### ملاحظة
Firebase structure كانت أصلاً subcollections (`users/{userId}/drq_threads/{threadId}`) — ما كان في مشكلة هيكلية، بس مشكلة في كمية البيانات. الخطة ذكرت تغيير الهيكل لكنه كان أصلاً سليم. المشكلة الحقيقية كانت تكرار حفظ كل threads في كل دقيقتين.

## Phase 4.1 — Arabic-Aware BM25

### الهدف
تحسين البحث داخل المحاضرات للغة العربية.

### المشكلة
الـ tokenizer القديم:
```typescript
split(/[\s\p{P}]+/u)
```
ما يتعامل مع:
- كلمات الوظيفة العربية (في، من، على، إلى، عن، أن، إن، هذا...)
- أشكال مختلفة من نفس الكلمة (إبراهيم، أبراهيم، ابراهيم)
- الحركات والتشكيل (السلام، السَّلام)

### التنفيذ

**1. إضافة `ARABIC_STOP_WORDS`:**
```typescript
const ARABIC_STOP_WORDS = new Set([
  "في", "من", "على", "الى", "إلى", "عن", "أن", "إن", "هذا", "هذه", "ذلك",
  "التي", "الذي", "كان", "يكون", "أو", "لا", "ما", "لم", "لن", "له", "لها",
  "هم", "هن", "كانت", "مع", "كل", "قد", "غير", "اذا", "إذا", "ثم", "حتى",
  "بين", "تحت", "فوق", "هو", "هي", "هل", "لقد", "ذلك", "تلك", "هؤلاء",
  "الذين", "اللذين", "اللواتي", "اللائي", "به", "بها", "لهم", "لهن",
  "فيه", "فيها", "منه", "منها", "عليه", "عليها", "عنه", "عنها",
]);
```

**2. إضافة `normalizeArabic()`:**
```typescript
function normalizeArabic(word: string): string {
  return word
    .replace(/[إأآا]/g, "ا")    // توحيد ألف
    .replace(/ى/g, "ي")          // ألف مقصورة → ياء
    .replace(/ة/g, "ه")          // تاء مربوطة → هاء
    .replace(/[\u064B-\u065F]/g, ""); // إزالة الحركات
}
```

**3. تحديث `tokenize()`:**
```typescript
function tokenize(text: string): string[] {
  return text.toLowerCase().split(/[\s\p{P}]+/u)
    .filter(Boolean)
    .map((t) => normalizeArabic(t))
    .filter((t) => !ARABIC_STOP_WORDS.has(t));
}
```

## Phase 4.2 — PostgreSQL Full-Text Search

### الهدف
البحث في محتوى المحاضرات عبر PostgreSQL tsvector — أسرع وأدق من BM25 اليدوي.

### المشكلة
- البحث الحالي: BM25 على paragraphs (نص منقسم إلى فقرات)
- يعمل فقط داخل محاضرة واحدة
- ما يبحث عبر كل المحاضرات
- يقارن query مع كل paragraph — O(n) لكل بحث

### التنفيذ

**1. تعديل `prisma/schema.prisma`:**
```prisma
model Lecture {
  // ...
  extractedText String?               @db.Text
  searchVector  Unsupported("tsvector")?
  // ...
  @@index([searchVector], type: Gin)
}
```

**2. إنشاء migration يدوي:**
```sql
-- Add extractedText for full-text search
ALTER TABLE "Lecture" ADD COLUMN "extractedText" TEXT;

-- Generated column: auto-updates when extractedText or title changes
ALTER TABLE "Lecture" ADD COLUMN "searchVector" tsvector
  GENERATED ALWAYS AS (to_tsvector('arabic', coalesce("extractedText", '') || ' ' || coalesce("title", ''))) STORED;

-- GIN index for fast full-text search
CREATE INDEX lecture_search_idx ON "Lecture" USING GIN ("searchVector");
```

**مزايا الـ GENERATED ALWAYS:**
- `searchVector` يتحدث تلقائياً لما يتغير `extractedText` أو `title`
- لا يحتاج تحديث يدوي
- الأمان: ما تقدر تكتب قيمة غير متوافقة

**3. تحديث `src/app/api/v1/search/route.ts`:**
- **قبل:** بحث بـ `title: { contains: q, mode: "insensitive" }`
- **بعد:** استخدام `$queryRawUnsafe` مع `plainto_tsquery('arabic', $1)`
- Fallback إلى `ILike` title لو فشل الـ full-text

**الكود:**
```typescript
const lecSql = `
  SELECT l.id, l.title, s.name AS "subjectName", m.id AS "moduleId", m.name AS "moduleName"
  FROM "Lecture" l
  JOIN "Subject" s ON s.id = l."subjectId"
  JOIN "Module" m ON m.id = s."moduleId"
  WHERE l."searchVector" @@ plainto_tsquery('arabic', $1)
  ORDER BY ts_rank(l."searchVector", plainto_tsquery('arabic', $1)) DESC
  LIMIT ${take}
`;
let lecRows = await prisma.$queryRawUnsafe<LecRow[]>(lecSql, q);
if (lecRows.length === 0) {
  // Fallback to ILike title search
  lecRows = await prisma.lecture.findMany({ where: { title: { contains: q, mode: "insensitive" } } });
}
```

- **سبب الإنشاء:** `useDrQChat.ts` يستدعي هذا الـ endpoint

- لكن الـ endpoint **ما كان موجوداً** — أي 404 silent
- **الآن:** موجود ويعمل full-text search مع fallback إلى ILike

## Phase C.3 — Server-Side Rate Limiting

### الهدف
نقل حماية الحصة اليومية من localStorage (اللي يتجاوز بمسح المتصفح) إلى Redis على السيرفر.

### المشكلة
- **قبل:** Rate limiting يعتمد على localStorage في المتصفح
- localStorage يتجاوز بمسح Cache
- مستخدم خبيث يقدر يستنزف حصة Gemini المجانية (30 RPM) بمسح localStorage

### التنفيذ

**إضافة rate limiting في `src/app/api/v1/ai/chat/route.ts`:**

```typescript
import { redisIncrWithExpire } from "@/lib/redis";

// بعد قراءة bodyJson
const isByok = !!(bodyJson as any)?.byokEnabled;
const rlKey = isByok ? `byok:${userId}` : `server:${userId}`;
const rlMax = isByok ? 100 : 20;
const rlWindow = isByok ? 3600 : 86400; // 1h BYOK / 1d server-key
const rlCount = await redisIncrWithExpire(rlKey, rlWindow);
if (rlCount > rlMax) {
  return NextResponse.json(
    { error: "Rate limit exceeded. Try again later." },
    { status: 429, headers: { "Retry-After": String(isByok ? 3600 : 86400) } },
  );
}
```

**الحدود:**
| المستخدم | الحد | النافذة | السبب |
|---|---|---|---|
| BYOK (مفتاح خاص) | 100 | 1 ساعة | منع DoS فقط — ما يأثر على حصتك |
| Server-key (مفاتيحك) | 20 | 1 يوم | حماية حصة Gemini المجانية |
